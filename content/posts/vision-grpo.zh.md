> Datawhale 组队学习《Agentic RL》Task03 的记录：vision-GRPO。教程见 [Agentic RL Lab](https://datawhalechina.github.io/agentic-rl-lab/experiments/getting-started/)，代码见 [datawhalechina/agentic-rl-lab](https://github.com/datawhalechina/agentic-rl-lab)。记录于 2026-11-21。

上一篇我用 GSM8K 跟了一遍 GRPO。这次换成几何选择题：图片、题干、四个选项。起初我以为要补一套视觉强化学习算法，读到训练脚本才发现，最值得停下来的其实是两个很具体的问题：一张图在序列里占了多少位置？模型写了一整段几何推导，程序最后给哪部分打分？

这次我把 100 步完整跑完，并把 SwanLab 里的原始指标重新统计了一遍。下面所有数字都来自两次运行的日志：第一次跑到第 68 步后中断，从第 65 步的检查点续训到第 100 步，重跑的三步只按最后一次计入。本地 `.swanlab` 文件解出的逐步指标与 SwanLab 云端返回的数据逐条比对过，100 步 × 6 个指标零差异；文中的曲线图直接截自 SwanLab 仪表盘。

- [第一次运行（第 1–68 步）](https://swanlab.cn/@jokerxuxu/agentic-rl-lab-vision-grpo/runs/l11udwhb) · [续训运行（第 66–100 步）](https://swanlab.cn/@jokerxuxu/agentic-rl-lab-vision-grpo/runs/rawcelig)

## 一条样本长什么样

GeoQA 的一条训练样本里有图、题干、四个选项、正确选项和题解。模型拿到前三项。正确选项留给评分函数，题解没有拼进 prompt。这一点决定了模型能学到什么：它可以尝试不同的推导，但训练程序只知道最终选项有没有答对。

![第 1 步用到的原图，以及送进模型的 prompt 结构](/images/agentic-rl/vg-sample-prompt.png)

上图左半边是第 1 步真正用到的样本（GeoQA id=9419），正确选项是 B。右半边是这条样本进入模型后的样子。

在 PyTRIO 里，传图要过两道关。先用模型的聊天模板确定图片插在哪里，再把那个位置换成携带真实图像字节的 `ImageChunk`。脚本还会给透明图片铺白底，避免几何图的透明背景转成黑色。最后得到的输入可以写成：

```text
EncodedTextChunk  +  ImageChunk  +  EncodedTextChunk
    模板前半段          几何图           模板后半段
```

这里容易忽略的是长度。一个 `ImageChunk` 在 Python 里是一个对象，但在模型序列里可以占多个位置。脚本用图像处理器算出预期的视觉 token 数，采样返回后再检查远端的 `input_tokens` 是否等于本地的 `len(prompt)`。后面构造训练样本，要靠这个长度找到回答从哪里开始。

## 图像参与预测，奖励落在回答上

假设整段图文 prompt 占 $P$ 个位置，模型生成了三个 token，记为 $a,b,c$。读 `build_grpo_datum` 时，我把数组缩短到只有这三个输出，才看明白代码里为什么写 `prompt_length - 1`。

| 训练输入的当前位置 | 在这个位置预测什么 | 填入的优势 |
|---|---|---|
| prompt 的前 $P-1$ 个位置 | 后续 prompt 内容，训练目标用占位值填充 | 0 |
| prompt 最后一个位置 | 回答的第一个 token $a$ | $A$ |
| 回答中的 $a$ | $b$ | $A$ |
| 回答中的 $b$ | $c$ | $A$ |

如果给足 $P$ 个零，第一个回答 token 的训练信号就会错开一位。图片虽然位于 prompt 内，它提供的信息仍然影响模型生成 $a,b,c$ 的概率。

这个实验从每段回答里提取最后一个可识别的方框选项，例如 `\boxed{B}`。匹配正确标签得 1 分，其余得 0 分。同一道题的 8 个回答共用一个平均奖励，每条回答的优势是 $A_i=r_i-\bar r$。把这个优势复制到该回答的各个 token，再连同采样时保存的逐 token 日志概率交给 `importance_sampling` 损失。这样做的代价也很直观：即使中间某一步几何推导有错，只要最后选对，评分函数也分辨不出来。

## 100 步训练结果：只有 34 步真的更新了参数

先用 SwanLab 自己的图说话。下面两张图直接截自 SwanLab 的「图表对比视图」：红色是第一次运行（第 1–68 步），绿色是续训（第 66–100 步），两次运行叠在同一条 step 轴上。

![SwanLab 图表对比视图：reward 与 train_datums](/images/agentic-rl/vg-swanlab-reward-datums.png)

左图是 reward。曲线几乎只在 0 和 1 之间跳：每步换一道新题，得分高低更多反映题目难度，而不是模型在逐步变强。

右图是 `train_datums`，也就是这一步实际送进前向反向的回答条数。它要么是 0，要么是 8——**没有中间值**。图上竖起的红绿尖峰数量，就是真正更新了参数的步数。

![SwanLab 图表对比视图：loss_mean 与平均输出长度](/images/agentic-rl/vg-swanlab-loss-length.png)

左图是 `trainer/loss_mean`。它只在发生过更新的步上有值，其余步一律缺失，连线因此是断开的；取值范围 0.0058 ~ 0.2247，平均 0.0629。量级之所以这么小，一部分原因是每步只做一次 LoRA 更新，另一部分原因是这 34 步里每一组 8 条回答都进了同一个 batch。

右图是每步的平均输出长度，峰值正好落在 1,024，也就是 `max_tokens` 的上限。

我再把同一份数据摊开看一遍，补上仪表盘本身看不出来的部分。

![每步得分，以及每步平均输出长度与 1024 token 上限的关系](/images/agentic-rl/vg-reward-format.png)

使用 Qwen3.5-4B、LoRA rank 32 和学习率 $4\times10^{-5}$。每步取 1 道题，每题采样 8 次，每条回答最多生成 1,024 个 token。

左图是每步 8 条回答的平均得分。绿色是组内有对有错的 34 步，它们真正进入了前向反向与优化器；粉色是 8 条回答同分的 66 步，组内相对优势全为零，脚本直接跳过。

右图是每步的平均输出长度。有 5 步（第 6、13、23、63、94 步）的 8 条回答全部写到 1,024 token 被截断，这 5 步的得分恰好全是 0。其余步分成两类：参与更新的 34 步平均输出 760 tokens，被跳过的 66 步平均只有 354 tokens。**长得长的回答，才是模型自己都没把握的那些回答。**

![800 条回答的去向，以及每步答对条数的分布](/images/agentic-rl/vg-answers-funnel.png)

把 800 条回答摊开看，结论比平均分更刺眼：

| 从日志统计的量 | 结果 |
|---|---:|
| 训练题数 / 采样回答数 | 100 / 800 |
| 成功提取选项 | 648 / 800（81%） |
| 匹配正确选项 | 640 / 800（80%） |
| 实际发生参数更新的步数 | 34 / 100 |
| 进入前向反向计算的回答数 | 272 / 800 |

我最意外的是，160 个零分回答里有 **152 个连选项都没提取到**，另外 8 个才是提取到了错误选项。仅凭日志，无法判断那 152 个回答中有多少推理出错、多少漏写了方框、多少在给出答案前就耗尽了 token。若想判断模型究竟卡在哪里，这批原始回答比一条平均 reward 曲线更值得看。

右图是每步答对条数的分布：5 步全错、61 步全对，两端合计 66 步，正是被跳过的那批。只有中间 34 步出现过同题有对有错的情况，参与更新的回答数恰好是 $34\times8=272$。

## 一次全对也会得到 $loss_{mean}=n/a$

这个现象看起来反常，代码里其实写得很直白：
```
if len(set(rewards)) == 1: continue
```
整组奖励相同就没有相对优势，跳过整组。

原运行的第 64 步是一个很好的对照：8 个回答全部符合格式，7 个答对。组平均奖励 0.875，所以正确回答的优势是 +0.125，错误回答的优势是 −0.875，8 个回答一起参与更新。第 65 步则是 8 个全对，优势全为零，脚本跳过整组。

需要说清楚的是，这里的 **80% 是训练过程中采样回答的正确比例**。同一道题重复作答 8 次，模型也在不断变化；每一步用的还是一道新题。课程报告的 71% 到 87% 来自固定的 100 道测试题，且教程每步训练 8 道题。我这次能确认的是训练跑通和最终权重保存；衡量模型是否真的变强，还需要让基座与训练后的模型在同一份测试集上各做一次。

## 两次中断，让我分清了"每组多少回答"和"一次请求发多少回答"

第一次照教程用每步 8 道题、每题 8 个回答。采样顺利，到了前向反向阶段才报图片数超限。原因藏在训练样本的结构里：每条有效回答都会连同原图构成一个 Datum。因此 8 张不同的图，最多会变成同一训练请求里的 64 个带图样本。我把每步题数降为 1，保留每题 8 个回答，随后成功完成了更新。

另两次中断发生在等待采样响应时。两次都在收到 163,840 字节时断开，这个巧合提示可以试着减小响应，但日志无法定位是哪一层关闭了连接。最后的做法是每次请求 2 个回答，同一版策略连续请求 4 次，凑齐 8 个以后才计算组平均。**拆请求的位置很重要**：如果每收到 2 个就算一次平均，同样的 8 个回答会得到不同的优势，实验也就变了。

![每步 rollout 耗时，以及两次运行的时间账](/images/agentic-rl/vg-step-cost.png)

从耗时上能看出那次中断有多难缠：同为一道题的 8 次回答，最快的一步只用了 4 秒，最慢的一步花了 29 分钟。第 24、42、61 步都超过了 17 分钟。100 步的 rollout 累计约 2.9 小时，第一次运行整体跑了 3.5 小时，最后一次续训只用了 28.3 分钟。

100 步运行第一次停在第 69 步，最近的完整训练状态保存在第 65 步。第 67 步实际发生过更新，单纯把进度数字改成 68 会漏掉它。我从第 65 步恢复模型和优化器，重新采样第 66 步，直到日志打印出第 100 步的 sampler 和 state 两个保存地址。以后再遇到中断，我会先找这两个信息：最后保存的是哪一步，以及报错出在采样还是参数更新。[原运行](https://swanlab.cn/@jokerxuxu/agentic-rl-lab-vision-grpo/runs/l11udwhb) · [续训运行](https://swanlab.cn/@jokerxuxu/agentic-rl-lab-vision-grpo/runs/rawcelig)
